======================================================================
一、项目背景
======================================================================

Swayframe 是一款：

Human-first, AI-native Motion Design & Compositing Software。

它不是简单模仿 After Effects 的编辑器。

其核心目标是：

人类创作者可以使用成熟、专业的传统编辑方式完成作品。

AI Agent 不仅能够操作软件已有功能，
还能够利用软件提供的底层可编程能力，
创造新的视觉效果和可复用创作工具。

目前 Swayframe 已经实现了大量基本功能，包括：

Canvas
Timeline
Keyframe
Motion Curve
Inspector
Scene Outliner
Compositing Graph
Effects
AI Agent
Desktop Application

具体实现情况以当前仓库为准。

但是当前存在一个重要问题：

AI Agent 的能力基本停留在：

操作已有图层、属性和效果。

例如：

当用户要求创建一个径向渐变时，

Agent 可能通过：

创建两个图层
添加 Gaussian Blur
叠加图层

来模拟效果。

这种方法虽然可能获得近似的视觉效果，
但无法准确表达用户真正需要的视觉处理操作。

同时：

当前许多 Effects 分散在不同面板，
Inspector、Timeline 和 Compositing Graph
之间缺乏足够统一的效果定义及执行机制。

本次升级必须从底层解决这些问题。

======================================================================
二、核心目标
======================================================================

最终让 Swayframe 具有三种 Agent 能力。

LEVEL 1 — OPERATOR

Agent 可以操作已有软件功能。

例如：

创建图层
修改属性
创建关键帧
移动对象
应用现有效果


LEVEL 2 — COMPOSER

Agent 可以通过组合已有功能构建复杂作品。

例如：

复杂动画编排
自动排版
多节点合成
效果链构建


LEVEL 3 — TOOLMAKER

Agent 可以创造新的程序化视觉效果。

例如：

生成 WGSL Shader
创建自定义 Generator
实现自定义 Image Filter
生成参数化视觉处理节点
将新效果保存为可复用工具


本次升级最重要的是：

真正实现 LEVEL 3 的技术基础。

但同时：

不要让 Agent 遇到任何问题都重新编写代码。

必须采用：

Existing Native Capability
        ↓
Reusable Composition
        ↓
Programmable Effect
        ↓
New Effect Creation

这样的能力选择策略。

已有原生功能能够准确完成时：

优先使用已有功能。

现有功能无法满足用户需求时：

才进入新的程序化效果创建流程。

======================================================================
三、开发原则
======================================================================

本次必须遵守：

1. 保留已有正常工作的功能。

2. 不为了新的 Effect Engine 重写整个软件。

3. 不直接让 AI 修改 Swayframe 核心源码。

4. 所有新功能必须兼容现有 Command System。

5. 所有正式 Scene 修改必须支持 Undo / Redo。

6. 所有可动画参数使用统一 Property<T> 系统。

7. Inspector / Timeline / Compositing Graph
   不能分别维护不同版本的效果实现。

8. Agent 创建的效果必须可编辑、可复用、可保存。

9. 不允许出现只有 UI、没有真实渲染能力的假功能。

10. 不允许以“完成架构文档”代替代码实现。

11. 不得破坏现有工程文件兼容性。

12. 不得绕过 DESIGN.md 规定的功能入口架构。

======================================================================
六、建立 Visual Capability Definition
======================================================================

根据当前项目 TypeScript 架构设计统一协议。

参考：

interface VisualCapabilityDefinition {
    id: string;

    name: string;

    version: string;

    category:
      | "fill"
      | "generator"
      | "filter"
      | "compositor";

    description?: string;

    inputs: PortDefinition[];

    outputs: PortDefinition[];

    parameters: ParameterDefinition[];

    implementation: ImplementationReference;

    capabilities: {
        animatable: boolean;
        realtime: boolean;
        deterministic: boolean;
    };
}

以上只是概念接口。

具体类型可以根据现有架构调整。

核心要求：

Definition：

描述一个效果是什么。

Instance：

描述某一次使用。

Preset：

描述一组保存的参数。

三者必须分开。

不要混为一个对象。

    ↓

    ↓

    ↓

======================================================================
三十二、性能与缓存
======================================================================

统一效果系统不能明显拖慢：

Canvas
Timeline
Playback

重点考虑：

Shader compilation cache

Effect pipeline cache

Parameter dirty state

Frame cache

Incremental rendering

Render Graph invalidation

实时调整参数时：

优先更新参数绑定。

不要每次拖动 Radius：

都重新编译 Shader。

只有源码、入口签名或相关管线配置改变时，
才触发必要的重新编译。

参数变化：

通常只更新 Uniform / Runtime Parameters。

具体优化以渲染后端实际能力为准。

======================================================================
三十三、效果错误处理
======================================================================

Compilation Error

Validation Error

Unsupported Feature

Missing Dependency

Runtime Failure

清晰诊断。

效果发生错误：

不能使整个工程丢失。

允许：

Disable Effect

Edit Source

Retry Compilation

Discard Draft

必要时：

使用安全的失败显示或旁路策略。
