# ============================================================
# SWAYFRAME 0.10
# RELIABLE AGENT ARCHITECTURE
# NATIVE SKILL RUNTIME
# AUTONOMOUS RECOVERY SYSTEM
# ============================================================

你现在开始对 Swayframe（SF）的 AI Agent 系统
进行一次以可靠性为最高优先级的架构升级。

本轮不是简单优化 Prompt。

不是继续给 Agent 增加工具。

不是开发更多视觉特效。

不是设计一个新的聊天界面。

而是从软件架构层面解决：

为什么 Swayframe 已经拥有大量编辑能力，
但 Agent 仍然不能稳定使用这些能力？

最终目标：

建立一套与具体 LLM Provider 尽量解耦的
Swayframe Native Agent Runtime。

使 Agent 即使更换不同模型，
也能够通过 SF 自身的能力发现、
语义操作、对象解析、参数验证、
Skill Runtime、事务执行、自主恢复
和结果验证机制，
尽可能稳定地完成创作任务。

本轮项目代号：

Swayframe Reliable Agent Architecture

版本目标：

0.10

开发原则：

RELIABILITY BEFORE CAPABILITY.

CORRECTNESS BEFORE AUTONOMY.

DETERMINISTIC EXECUTION BEFORE LLM RETRY.

但是 Agent 长期存在以下问题：

1. createText 参数无效。

2. setFill 参数无效。

3. setFill layerId 无效 UUID。

4. creation.tasks.dependencies 与执行顺序冲突。

5. Plan Validation 失败后直接终止。

6. 执行过程中发生错误后难以恢复。

7. 已创建对象无法被后续步骤可靠引用。

8. 部分工具参数与实际能力定义不一致。

9. Agent 上下文包含大量重复工具说明。

10. Agent 查询大量工具后仍可能无法执行任务。

11. 简单错误可能导致整个任务失败。

12. 用户无法判断失败究竟发生在哪个阶段。

13. 单元测试通过并不代表真实 Provider 能稳定创作。

14. Agent 有时能完成前期规划，
    但后期实际操作失败。

15. 遇到问题后反复调用 LLM，
    却没有真正改变错误计划。

此前 Swayframe 已经完成多轮 Agent 审计。

============================================================
第五部分：Semantic Action Compiler
============================================================

这是本轮的重要架构升级。

减少模型直接构造复杂底层命令的负担。

LLM 的主要职责是：

表达用户意图。

软件的职责是：

将合法意图编译为正确 Command。

例如用户：

“创建一个居中的蓝色径向渐变矩形。”

模型可以输出较高层的：

Create Shape

Set Gradient Fill

Place at Composition Center。

随后：

Semantic Action Compiler

负责：

解析当前 Composition。

确定实际画布尺寸。

确定 Shape 类型。

创建真实 Layer。

取得真实 Layer ID。

构造合法 Gradient Parameters。

调用已有 Command。

整个过程中：

不要求模型自行计算所有内部字段。

但：

不能把 Action Compiler
做成第二套编辑引擎。

它只负责：

Resolve

Normalize

Validate

Compile。

最终：

仍然调用正式 Command System。

复杂操作可以由多个 Command
组成一个 Transaction。

简单、稳定的工具可以继续直接调用。

不要强迫全部操作通过冗长的语义编译流程。

============================================================
第六部分：Object Reference System
============================================================

这是 P0 任务。

Agent 不应该依靠自行编造 UUID
来引用刚创建的对象。

必须支持：

Existing Object Reference

Current Selection Reference

Step Result Reference

Graph Node Reference。

例如：

Step 1：

Create Rectangle。

返回：

actualLayerId。

Step 2：

Set Fill。

引用：

Step 1 的 Layer。

Step 3：

Set Position。

继续引用：

Step 1 的 Layer。

Step 4：

Add Keyframe。

继续引用：

同一个 Layer 的 Property。

真实 ID 由程序管理。

模型使用：

明确的对象引用。

对象解析必须验证：

Object Exists

Object Type

Composition

Scope

Current Draft State。

如果引用无法解析：

返回结构化错误。

不能：

猜测 UUID。

不能：

根据相似名称随机选择对象。

不能：

把 Graph Node ID
当作 Layer ID。

不能：

把 Task ID
当作 Layer ID。

已有合法 UUID 操作应保持兼容。

不能为了提高成功率
直接放宽 UUID 校验。

============================================================
第七部分：Task Dependency Engine
============================================================

这是 P0 任务。

必须解决：

creation.tasks.dependencies

与实际执行顺序冲突的问题。

建立明确的任务依赖图。

支持：

Dependency Validation

Missing Dependency Detection

Cycle Detection

Producer / Consumer Binding

Stable Topological Sort

Execution Order Validation。

例如：

Analyze Typography
      ↓
Create Text
      ↓
Set Font。

如果模型生成顺序错误，
但依赖图合法且操作允许安全重排：

程序应能够确定性修复。

如果存在循环依赖：

禁止盲目重排。

如果缺少生产者任务：

进入受限重新规划。

如果操作之间存在不可交换的副作用：

不能为了完成拓扑排序
而改变用户要求的语义。

对于依赖未来执行结果的操作：

使用：

DEFERRED VALIDATION。

待依赖真实产生后：

重新验证。

不得：

因为前面出现 READ
就跳过后续 WRITE 的语义验证。

============================================================
第八部分：Autonomous Recovery System
============================================================

这是本轮最重要的能力之一。

目标：

Agent 不再因为一个可恢复错误
立即终止整个创作任务。

建立：

DIAGNOSE
→
CLASSIFY
→
REPAIR
→
REVALIDATE
→
CONTINUE。

优先支持以下恢复类型：

1. Plan Dependency Recovery

2. Tool Argument Recovery

3. Object Reference Recovery

4. Context Refresh

5. Execution Recovery

6. Result Verification Recovery

7. Transient Provider Recovery。

必须优先尝试：

Deterministic Repair。

例如：

合法的依赖重排：

拓扑排序。

明确的对象引用：

Step Result Binding。

缺失可选参数：

使用正式 Schema Default。

上下文版本失效：

重新读取对应 Draft。

只有确定性恢复无法解决时：

才调用 LLM 重新规划。

不能：

任何错误都重新发送整个 Prompt。

============================================================
第九部分：恢复策略与安全边界
============================================================

建立统一恢复分类：

AUTO_REPAIRABLE

MODEL_REPAIR_REQUIRED

USER_ACTION_REQUIRED

NON_RECOVERABLE。

错误分类必须由程序决定。

不能完全依赖模型自行判断。

自动恢复不得：

修改用户未授权对象。

扩大原始执行 Scope。

无限重试。

静默忽略失败步骤。

执行不完整的 JSON。

绕过 Tool Validation。

覆盖用户执行期间的新修改。

重新执行不具备幂等性的创建操作。

修改 Swayframe 内核源码。

安装未受信任的外部代码。

对于涉及：

删除已有作品

大范围重构

外部 API 费用

新权限

外部数据传输

等情况，

必须遵守现有授权机制。

无法安全恢复时：

明确说明阻塞原因。

不要假装继续成功。

Skill 负责：

描述某类任务的标准流程。

声明前置条件。

声明所需能力。

声明执行范围。

Semantic Action Compiler

Command System

Agent Transaction

Recovery Controller。

禁止：

Skill 绕过 Command System
直接修改 Scene JSON。

禁止：

Skill 自己维护对象 UUID 映射。

禁止：

每个 Skill 自己实现一套错误恢复。

这些都属于 Core Runtime。

第十九部分：不同 LLM Provider 兼容
============================================================

Provider Capability Profile。

Vision Support

Context Window

Tool Schema Compatibility

Provider Adapter 负责：

    ↓

    ↓
Structured Plan
    ↓
SF Runtime。

允许使用受限 Structured Plan 模式。

但：

所有生成计划仍必须经过
同一套 Schema 和语义验证。

不可靠或不支持的能力：

必须明确标记。

禁止宣称所有 API
拥有完全相同的能力。

不得绕过统一 Agent Runtime。
