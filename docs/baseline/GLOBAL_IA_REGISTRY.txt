你现在要对整个 Swayframe 进行一次最高优先级的：

======================================================================
GLOBAL INFORMATION ARCHITECTURE
+
FEATURE DISCOVERABILITY
+
SCALABLE FEATURE ENTRY SYSTEM
重构
======================================================================

这不是一次普通 UI 美化。

也不是简单：

“把按钮重新排列得好看一点”。

当前真正的问题是：

随着功能数量不断增加，

每个功能都在开发完成后临时寻找入口，

导致：

- 同类功能分散；
- 高频功能被隐藏；
- 低频功能长期占据一级界面；
- 相同功能出现多个重复入口；
- Canvas / Scene / Inspector / Timeline / Graph 职责混乱；
- 菜单越来越深；
- 用户无法预测功能应该出现在哪里；
- Codex 每次新增功能都可能进一步破坏现有结构；
- UI Shell 与具体功能耦合越来越严重；
- 功能越多，未来开发阻力越大。

本轮的最终目标是：

======================================================================
即使未来 Swayframe 再增加数百个功能，

它们仍然能够按照稳定规则自动归类到合理区域，

而不需要不断重构整个 UI。
======================================================================

核心原则：

DO NOT organize features by implementation history.

Organize features by:

OBJECT
+
TASK
+
FREQUENCY
+
CONTEXT

任何新功能：

必须先回答：

“它属于哪个用户任务？”

然后才决定：

“它在哪里出现？”

第九阶段：建立 Feature Registry

设计类似：

interface FeatureDefinition {
    id: string;

    title: string;

    domain: FeatureDomain;

    objectTypes?: ObjectType[];

    tasks: TaskType[];

    frequency: FeatureFrequency;

    contexts: ContextKey[];

    commandId: CommandId;

    placement: {
        canonical: ContributionPoint;
        secondary?: ContributionPoint[];
    };

    shortcut?: ShortcutDefinition;

    keywords?: string[];

    icon?: IconId;

    order?: number;
}

例如：

registerFeature({
    id: "layer.precompose",

    domain: "scene",

    objectTypes: ["layer"],

    tasks: ["organize"],

    frequency: "F3",

    contexts: [
        "layerSelection"
    ],

    commandId:
        "layer.precompose",

    placement: {
        canonical:
            "context.layer",

        secondary: [
            "menu.layer",
            "commandPalette"
        ]
    }
})

完成重构后：

不要立刻实现这些功能。

只做模拟测试。

假设未来增加：

Motion Trail

问：

需要修改哪些文件？

理想答案：

新增：

MotionTrailFeature

register command

register feature

register inspector/effect contribution

少量 renderer code

不应该：

修改 AppShell

修改 TimelineHeader

修改 MainToolbar

修改多个 Context Menu。


再假设增加：

Chromatic Aberration Effect。

理想：

register effect

renderer implementation

Inspector 自动出现。


再假设增加：

Optical Flow Node。

理想：

register graph node

Graph Add Node 自动出现。


再假设增加：

AI Auto Layout。

理想：

register assistant action

Command Palette 可搜索。

如果每新增一个功能：

仍然需要改：

5–10 个核心 UI 文件，

说明本轮架构仍未成功。

======================================================================
第四十四阶段：最终验收
======================================================================

最终问自己：

如果明天增加一个新功能，

开发者是否首先知道：

它是什么类型？

属于哪个 Domain？

作用于哪个 Object？

属于哪个 Task？

使用频率是多少？

需要什么 Context？

Canonical Home 在哪里？

是否需要 Shortcut？

是否需要 Context Menu？

然后：

只注册 Feature

就可以进入：

正确 UI。

如果答案是：

是，

则本轮成功。


如果仍然是：

“先做功能，然后看看哪个地方还有空位放按钮”，

则本轮失败。
