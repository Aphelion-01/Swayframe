# ============================================================
# SWAYFRAME AGENT CORE V2
# CONTROLLED RECONSTRUCTION PROJECT
# ============================================================

项目：

Swayframe（SF）

任务：

重新构建 Swayframe AI Agent 的核心架构。

项目代号：

AGENT CORE V2

开发目标：

建立一套简洁、可靠、可扩展、
与具体 LLM Provider 尽量解耦的
原生 AI Agent 执行系统。

本轮采用：

PARALLEL REPLACEMENT

而不是：

IN-PLACE PATCHING。

核心原则：

RELIABILITY FIRST.

ONE EXECUTION STATE OWNER.

INCREMENTAL PLANNING.

DETERMINISTIC EXECUTION.

SAFE RECOVERY.

MEASURABLE QUALITY.

============================================================
第一部分：为什么需要重建
============================================================

Swayframe 自 0.9.0 起，
已经多次修复 AI Agent。

但真实使用中，
基础任务仍然频繁失败。

已出现过：

createText 参数无效

setFill 参数无效

layerId 无效 UUID

creation.tasks.dependencies
与执行顺序冲突

shape.rectangle 未注册

规划阶段工具调用越权
或超过次数限制

Completed step cannot be replayed

STALE_OBJECT_REFERENCE

等问题。

这些问题涉及：

工具契约
能力注册
规划
对象引用
状态管理
恢复
事务
验证。

旧 Agent 在多轮修复后
仍未达到预期可靠性。

因此决定：

保留现有编辑器基础设施。

冻结旧 Agent 执行架构。

建立全新的 Agent Core V2。

重要：

不要因为历史上发生过这些错误，
就直接假设所有问题仍存在于当前版本。

先记录当前仓库状态与可复现基线。

新架构的价值必须通过
相同任务的前后对照证明。

第三部分：冻结旧 Agent
============================================================

首先：

检查 Git Status。

保存未提交修改。

建立独立开发分支或工作树。

不要删除用户已有修改。

不要删除旧 Agent。

保持：

禁止继续为 V1 增加新功能。

例如：

Legacy V1

Core V2

默认仍使用当前正式稳定路径，
直到 V2 通过验收。

不要在普通用户界面中
同时启用两个写入执行器。

============================================================
第四部分：新架构设计
============================================================

V2 最小核心包括：

1. Provider Bridge

2. Agent Planner

3. Task Runtime

4. Editor Adapter

5. Result Verifier

6. Recovery Policy

不要一开始就重新创建：

不要求每一个逻辑职责

优先使用：

简单、类型安全、可测试的模块。

============================================================
第五部分：Provider Bridge
============================================================

优先复用现有可工作的：

Provider Configuration

Credential Management

HTTP Transport

Streaming

Cancellation

Token Accounting。

不要为了 V2
重写所有 API 网络代码。

V2 需要获得统一结构的：

Normalized Model Response。

Provider Bridge 应隔离：

DeepSeek

OpenAI-compatible APIs

Claude

OpenRouter

SiliconFlow

以及当前真实支持的其他服务。

但不得假设所有 Provider
都支持同样的 Tool Calling 能力。

必须识别：

Structured Output

Function Calling

Vision

Streaming

Cancellation

Context Limits。

对于不存在的能力：

明确报告。

不能虚构支持。

所有 Provider
最终进入同一个 V2 Runtime。

============================================================
第六部分：Agent Planner V2
============================================================

重新设计 Planner。

核心原则：

LLM 负责：

理解用户目标。

选择创作策略。

决定需要哪些能力。

生成高层任务计划。

但不应该：

一次性构造大量依赖未来状态的
底层 Command 参数。

Planner 应优先输出：

Structured Task Intent。

例如：

Create Rectangle

Apply Gradient

Create Text

Animate Opacity。

具体实现时：

根据真实运行状态，
逐步生成合法 Action。

对于复杂创作：

允许拥有完整高层规划。

但执行层不能依赖
所有未来对象 ID 已经存在。

============================================================
第七部分：Incremental Execution
============================================================

这是 V2 最重要的改变之一。

采用：

PLAN
→
EXECUTE SMALL BATCH
→
OBSERVE STATE
→
CONTINUE。

每批操作必须：

目标明确。

依赖可解析。

参数可验证。

作用域合法。

执行后状态可检查。

不要：

要求模型提前生成
几十个不可修改的 Tool Calls。

但也不要：

每执行一个简单属性修改
就重新请求 LLM。

同一个确定性子任务中的连续命令，
应尽量由 Runtime 直接执行。

============================================================
第八部分：Task Runtime
============================================================

建立唯一：

Task Runtime。

它是 V2 执行状态的唯一权威来源。

至少管理：

Task ID

Task Goal

Current Phase

Current Draft

Current Scene Version

Current Targets

Step States

Step Results

Object References

Completed Actions

Pending Actions

Errors

Recovery Attempts

Execution Budget。

每个步骤明确状态：

PENDING

READY

RUNNING

SUCCEEDED

FAILED

CANCELLED。

如有需要：

增加等待用户确认、
等待外部能力等状态。

不得：

一个 Planner 维护执行状态，
另一个 Recovery Controller
维护另一套执行状态。

============================================================
第九部分：Object Identity
============================================================

模型不应自行生成 Layer UUID。

Runtime 应支持：

Existing Object

Selected Object

Step Result Object。

例如：

Step A：

Create Rectangle。

Editor 返回：

真实 Layer ID。

Runtime：

记录 Step Result。

Step B：

Apply Fill。

Runtime：

从 Step A 获取真实 ID。

执行前：

检查目标存在。

检查目标类型。

检查目标属于当前 Composition。

检查目标位于允许修改范围。

然后：

调用正式 Command。

不得：

将 Task ID 当作 Layer ID。

不得：

将 Graph Node ID 当作 Layer ID。

不得：

根据对象名称随意猜测 ID。

============================================================
第十部分：Capability Discovery
============================================================

不要为 V2
重新创建一份独立的能力数据库。

复用当前实际执行系统中
权威的 Capability / Command / Effect 定义。

Planner 需要知道：

真实可用的操作。

真实操作参数。

适用对象类型。

参数范围。

执行约束。

输出类型。

Capability ID

Tool Name

Command ID

可以不同。

但必须有明确、可验证的映射。

例如：

Create Rectangle

最终一定要映射到
真实存在的创建命令。

禁止：

Planner 使用未注册能力。

禁止：

依赖 LLM 自行猜测工具名称。

============================================================
第十一部分：Typed Actions
============================================================

建立一组少量、稳定的：

Typed Semantic Actions。

第一阶段只支持：

Create Shape

Create Text

Set Property

Set Fill

Add Effect

Add Keyframe

Modify Keyframe。

不要一次性开放所有工具。

每个 Action：

必须有明确 Schema。

明确输入和输出。

明确是否需要对象目标。

明确能否参与事务。

明确成功条件。

禁止：

使用任意 Record<string, unknown>
承载所有复杂业务参数，
然后在执行深处才检查。

复杂参数应来自正式能力定义。

============================================================
第十二部分：Editor Adapter
============================================================

V2 通过：

Editor Adapter

访问现有编辑器。

Editor Adapter 提供：

Read Scene

Read Selection

Read Composition

Query Capabilities

Execute Command

Inspect Result

Render Frame。

但 Adapter 不应：

独立修改 Scene。

独立维护工程状态。

重新实现 Effect Engine。

绕过 Transaction。

V2 所有正式修改
最终仍必须进入：

共享 Command System。

============================================================
第十三部分：事务与草稿
============================================================

复用现有：

Agent Draft Transaction。

如果现有事务系统已可靠，
不得重新实现。

V2 的所有操作：

先执行在隔离 Draft。

不直接改变正式工程。

在任务结束时：

验证目标状态。

检查 Scope。

检查 Base Version。

生成 Proposed Changes。

得到适用的提交授权后：

一次 Commit。

对于用户已有内容的重大修改，
不得未经授权提交。

Undo：

一次撤销本次 Agent 提交。

============================================================
第十四部分：不重放已完成步骤
============================================================

这是本轮重点。

禁止：

简单地从步骤一重新执行
已经完成的非幂等命令。

例如：

Create Layer 成功。

后续 Add Effect 失败。

恢复时：

不得再次创建相同 Layer。

正确做法：

从当前有效 Draft
继续处理失败步骤。

如果 Draft 无法安全继续：

必须使用明确的 Checkpoint。

从可信状态重建。

重新绑定新的真实对象 ID。

不得：

机械复用旧 Draft 的对象 ID。

不得：

用重复执行整个 Plan
作为默认恢复策略。

对于步骤状态：

SUCCEEDED

只能在合法的状态恢复流程中转换。

不得：

因为 LLM 返回了同名步骤
就自动重新执行。

============================================================
第十五部分：Recovery V2
============================================================

建立简单、受限的恢复策略。

先支持：

Invalid Arguments

Invalid Object Reference

Missing Capability

Dependency Error

Command Rejection

Verification Failure。

优先：

Deterministic Recovery。

例如：

缺少合法默认参数：

从 Schema 获取。

已创建对象引用：

从 Step Result 获取。

任务依赖顺序错误：

在语义允许时确定性重排。

如果需要模型判断：

只发送失败步骤、
必要上下文及结构化错误。

不得：

将整个巨大 Plan 和所有日志
反复发送给模型。

不得：

无限调用 LLM。

不得：

为了恢复突破用户授权。

============================================================
第十六部分：错误协议
============================================================

所有错误使用统一结构。

至少包含：

Error Code

Phase

Action ID

Target Reference

Relevant Field

Expected Value

Actual Value

Recoverable

Recovery Strategy

Message。

禁止：

只返回参数无效。

禁止：

将完整嵌套错误对象
重复塞入模型上下文。

禁止：

错误字符串决定全部恢复策略。

禁止：

截断 JSON 导致无法解析。

普通用户看到：

简洁错误说明。

开发者看到：

完整脱敏诊断。

============================================================
第二十八部分：防止新架构再次失控
============================================================

为 V2 制定明确架构限制。

规则一：

只有一个任务状态管理者。

规则二：

只有一个正式 Command 执行入口。

规则三：

对象引用必须由 Runtime 解析。

规则四：

Capability 必须来自真实 Registry。

规则五：

Provider 不包含 Scene 编辑逻辑。

规则六：

Recovery 不拥有独立 Scene。

规则七：

Skill 不拥有独立执行器。

规则八：

Planner 不能绕过 Validator。

规则九：

完成的非幂等步骤不能直接重放。

规则十：

未经验证不能标记任务完成。

以后新增 Agent 能力：

必须遵守以上规则。

如果新增一个模块
需要违反这些限制：

先重新审查设计。

不能随意增加新的并行状态系统。
