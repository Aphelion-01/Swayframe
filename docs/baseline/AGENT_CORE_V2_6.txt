项目名称：

Swayframe（SF）

当前阶段：

Agent Core V2-6

开发目标：

在现有 Agent Core V2 的基础上，
完善自主故障恢复能力，
验证复杂多步骤任务的执行稳定性，
并为后续正式接入 Swayframe Agent UI
建立可靠的验收标准。

本轮核心原则：

DO NOT REBUILD THE AGENT AGAIN.

RECOVER INSTEAD OF RESTART.

PRESERVE COMPLETED WORK.

ONE RUNTIME, ONE EXECUTION STATE.

DETERMINISTIC REPAIR FIRST.

LLM REPAIR ONLY WHEN NECESSARY.

VERIFY BEFORE COMMIT.

NO UNBOUNDED RETRIES.

STEP 2：

============================================================
八、确定性恢复优先
============================================================

对于可通过程序解决的错误：

不得优先调用 LLM。

例如：

情况一：

步骤引用已完成的 Create Result。

处理：

从 Runtime Step Result Map
取得真实对象 ID。


情况二：

计划中的合法依赖顺序错误。

处理：

在不改变操作语义的条件下
进行依赖排序。


情况三：

缺少明确的可选参数。

处理：

使用正式 Schema Default。


情况四：

上下文需要刷新。

处理：

重新读取当前可信 Draft State。


情况五：

模型提交重复的失败参数。

处理：

根据 Error Fingerprint
阻止相同输入的无意义重试。


但不得：

把非法参数任意修改为
某个看似合理的值。

例如：

Radius = -1

不能未经语义判断
随意转换为 Radius = 1。

除非：

正式参数契约明确规定
可采用这种规范化规则。

否则必须要求模型重新决定参数。

============================================================
九、LLM-Assisted Recovery
============================================================

当程序不能确定性修复时：

允许调用真实模型进行局部纠错。

重点：

只纠正失败的 Action。

不要重新生成整个创作任务。

恢复请求应该包含：

Original Task Goal Summary

Failed Action

Structured Error

Relevant Capability Schema

Current Valid Draft Summary

Available Repair Scope。

不得：

发送完整历史执行日志。

重复发送所有 Tool Schema。

重复发送完整 Scene JSON。

反复嵌套 Diagnostics。

示例：

{
  "action": "setFill",
  "error": {
    "code": "ARGUMENT_INVALID",
    "field": "radius",
    "received": -1,
    "expected": "positive number"
  },
  "allowedRepair": "arguments-only"
}

模型返回：

修正后的 Action Arguments。

Runtime：

重新验证。

验证通过：

执行。

验证失败：

根据恢复预算决定是否继续。

特别注意：

LLM 不能通过修复参数
偷偷修改目标对象。

例如：

原 Action 目标是 Layer A。

模型不能将目标改成 Layer B，
除非任务语义和授权明确允许。

============================================================
十、Recovery Budget
============================================================

恢复必须具有明确限制。

建议默认：

单个失败 Action：

最多 2 次模型修复。

同一错误指纹：

相同输入不得重复尝试。

单任务：

设定独立 Recovery Budget。

整体请求数、Token 与耗时：

必须受总任务预算约束。

不得：

无限重试。

不得：

循环调用模型
直到用户 API 额度耗尽。

特别区分：

Execution Action Count

Model Request Count

Recovery Attempt Count。

不能将：

一次恢复中的模型请求

错误地计入：

已经成功的工具操作数量。

所有次数应在 Trace 中明确可见。

============================================================
十一、恢复终止条件
============================================================

出现以下情况：

必须正确终止。

1. 用户主动取消。

2. 原始操作超出授权范围。

3. 正式工程版本发生冲突，
   且无法安全处理。

4. 请求真实不存在的能力，
   且没有合法替代。

5. 无法解析目标对象。

6. 同一错误重复出现，
   且修复方案没有变化。

7. 恢复预算耗尽。

8. 模型持续返回无效输出。

9. 执行结果无法通过安全验证。

终止时：

不得提交失败 Draft。

不得修改无关用户内容。

必须输出：

失败阶段。

具体原因。

安全执行过的步骤。

是否保留可供用户检查的草稿。

是否需要用户操作。

不能：

仅显示“任务失败”。

Agent 分析很久，
最终因为一个错误停止。

这不仅影响体验，
还造成 Token 浪费。

本轮重点优化：

恢复成本。

而不是整体重写 Prompt System。

检查：

每次失败后是否发送完整上下文。

是否重复发送全部工具 Schema。

是否重复发送完整 Scene。

是否重新生成整个 Plan。

是否重复查询已知 Capability。

是否在没有实际变化时再次请求模型。

目标：

局部修复只需要局部信息。

长任务使用结构化工作状态摘要。

同一无效修复不重复请求。

已完成步骤不重新规划。

统计：

Total Input Tokens

Total Output Tokens

Recovery Input Tokens

Recovery Output Tokens

Recovery Requests

Repeated Invalid Requests

Task Duration。

注意：

不能只追求减少 Token，
却降低任务正确率。

二十四、公平的 V1 / V2 对照
============================================================

此前真实测试存在：

V1 展示的 Tool Catalogue
与 Test Host 实际 Allowlist
不一致的问题。

本轮必须消除这种干扰。

建立严格匹配的对照环境：

相同 Provider。

相同 Model。

相同 User Request。

相同初始 Composition。

相同可用编辑能力。

相同授权范围。

相同预算上限。

尽量相同采样设置。

V1 和 V2 的内部执行接口可以不同。

不要求两套系统
采用相同的 Planner。

但必须保证：

用户能够使用的实际编辑能力相同。

不得：

向 V1 展示无法使用的工具。

不得：

只给 V2 提供额外隐藏能力。

同时：

真实用户体验测试
与统一工具子集对照
应分别统计。

如果 V1 使用了被限制的测试能力集，
不得将其称为完整 V1 产品体验。

============================================================
二十六、Canary Readiness
============================================================

本轮目标：

评估 V2 是否具备进入
受控 Canary 的条件。

不要求直接正式替换 V1。

Canary 必须满足：

1. V2 基础任务通过真实 Provider 验证。

2. 自动恢复通过离线故障注入。

3. 真实模型参与恢复得到明确验证，
   或将其列为阻塞项。

4. 长任务没有发现严重状态错误。

5. 正式工程不存在未经授权的修改。

6. 成功任务正确 Commit。

7. Undo / Redo 正常。

8. 失败任务不错误提交。

9. 开发者可查看 Trace。

10. 用户可以明确选择 V2。

11. V1 仍可作为回退方案。

12. V1 / V2 不同时写入正式工程。

如果不满足：

保持：

CANARY NOT READY。

不得：

因为新版本构建成功
就自动设置 V2 为默认。
