============================================================
四、本轮核心问题：连续会话
============================================================

目前 V2 已经能够完成独立任务。

但是专业动画创作并非一次性操作。

用户可能连续发送：

第一次：

创建三个矩形。

第二次：

把第二个矩形改成蓝色渐变。

第三次：

让刚才修改的矩形在两秒内移动。

第四次：

把这个矩形缩小一点。

第五次：

撤销刚才的动画，但保留渐变。

此时：

Agent 必须准确理解每一轮操作
与现有工程对象之间的关系。

不能：

每次对话重新创建矩形。

不能：

根据图层名称猜测目标。

不能：

凭模型记忆编造 UUID。

不能：

使用过期的 Step Result。

不能：

把上次任务的临时执行引用
误当作永久对象身份。

必须建立可靠的连续任务上下文。

============================================================
五、Session State 设计
============================================================

检查当前 V2 TaskRuntime
是否已经支持跨任务 Session。

优先复用现有结构。

建立清晰区分：

Task State

和：

Conversation Session State。

Task State：

只负责当前任务的执行。

包含：

Task ID

Draft

Steps

Step Results

Recovery Attempts

Execution Budget

Commit Status。

Session State：

负责连续对话中必要的上下文。

包含：

Session ID

Current Project Identity

Current Composition Identity

Last Accepted Task

Recently Created Objects

Recently Modified Objects

Current User Selection

Relevant User Intent

Conversation Turn References。

注意：

Session State 不应变成
第二套 Scene Model。

正式对象状态仍然以：

Current Project / Scene

为准。

Session 只保存必要引用和上下文。

不得：

在 Session 中维护与真实 Scene
互相独立的对象属性副本。

不得：

依靠完整聊天记录
恢复所有工程状态。

六、跨轮次对象引用
============================================================

这是本轮 P0。

需要支持以下情况：

CASE 1：

引用刚刚创建的对象。

CASE 2：

引用上一轮创建的对象。

CASE 3：

引用当前选中的对象。

CASE 4：

引用当前 Composition 中的已有对象。

CASE 5：

引用用户通过 GUI 手动修改过的对象。

CASE 6：

引用被用户删除的对象。

CASE 7：

引用 Undo 后已经不存在的对象。

CASE 8：

引用保存并重新打开后仍然存在的对象。

所有引用必须解析为：

真实当前 Scene 中存在的对象。

必须检查：

Project Identity

Composition Identity

Layer ID

Object Type

Current Existence

Scope

Lock State

Current Version。

跨任务引用不能单纯复用
上一个 TaskRuntime 的临时 Step Result Map。

成功提交后的对象引用
应当转换为可以在当前正式工程中
重新验证的对象引用。

如果引用已经失效：

必须明确返回错误。

如果多个对象符合描述：

不得随机选择。

应当请求明确目标，
或使用用户明确提供的选区消歧。

用户增加关键帧。

用户删除效果。

用户切换 Composition。

用户更改 Selection。

用户执行 Undo。

用户执行 Redo。

必须获取可信当前状态。

当任务执行过程中：

正式工程状态发生改变，

必须继续遵守：

Baseline Conflict Protection。

不能：

因为是连续 Session，
就允许覆盖并发修改。

用户接受。

Commit A。

用户接受。

用户接受。

Commit C。

撤销对应操作。

把 Turn 1 创建的三个矩形全部删除。

“撤销刚才的动画，但保留渐变。”

必须区分：

撤销最近一次正式事务

和：

对动画属性进行有作用域的反向编辑。

只有语义明确且满足当前历史/状态条件，
才能确定性执行。

如果历史操作之后又进行了
不相关的 GUI 修改，

不得盲目撤销错误的事务。

需要检查真实命令历史与当前状态。

禁止：

直接修改 Scene JSON
模拟 Undo。

十七、连续任务故障恢复
============================================================

必须测试：

一个 Session 中
前两轮已成功提交。

第三轮出现可恢复错误。

此时：

第三轮失败或恢复
不得影响前两轮的正式结果。

例如：

Turn 1：

创建背景。

Commit A。


Turn 2：

创建标题。

Commit B。


Turn 3：

添加动画时参数出错。

进入 Recovery。


正确行为：

保留背景。

保留标题。

仅修复当前动画任务。

不得：

重新执行前两轮的创建操作。

不得：

把三个轮次合并成一个
不可控的恢复事务。

如果 Turn 3 无法恢复：

前两轮已接受的修改
仍然保持有效。

============================================================
十九、恢复与撤销行为边界
============================================================

自主恢复只作用于当前运行任务。

不得：

为了恢复当前任务，
自动撤销用户前一轮已经接受的作品。

不得：

在错误恢复中修改其他 Session 的对象。

不得：

从被拒绝的 Draft 中读取所谓
“已经创建成功”的正式对象。

如果当前 Task Draft 不再可信：

允许安全丢弃当前 Draft。
